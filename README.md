# 퇴사 후 자산관리

소득이 끊긴 기간의 자산관리는 수익률 문제가 아니라 **시간 문제**다.
이 리포지토리는 하나의 질문에 답하기 위해 있다.

> 지금 속도로 살면 몇 달 버티는가. 그 답을 바꾸려면 무엇을 건드려야 하는가.

## 30초 사용법

```bash
pip install -r requirements.txt

./fin                      # 한 화면 요약 — 자산 · 소진속도 · 런웨이 · 기한
./fin runway               # 시나리오별 런웨이
./fin report --month 2026-08   # 그 달 지출 뜯어보기
./fin checklist            # 퇴사 후 행정, 남은 기한
```

기록은 두 줄이면 끝난다.

```bash
./fin spend 식비 12000 --memo "점심 배달"      # 쓴 돈
./fin earn 구직급여 189만                      # 들어온 돈
./fin snapshot --set main_checking=5200000     # 월말 잔액
```

아직 아무것도 안 채웠다면 예시 데이터로 먼저 결과 화면을 볼 수 있다.

```bash
./fin --data-dir data/example
```

## 처음 한 번 해야 하는 설정

`data/` 안의 파일 네 개를 채우면 된다. 전부 사람이 읽고 고치는 형식이다.

| 파일 | 무엇을 적나 |
|---|---|
| `profile.yaml` | 퇴사일, 목표 런웨이, 비상금, 앞으로의 조정 |
| `accounts.yaml` | 계좌와 그 **유동성 등급** |
| `cashflow_plan.yaml` | 앞으로 들어올 돈(실업급여 등), 시점을 아는 큰 지출 |
| `scenarios.yaml` | 어떤 가정으로 런웨이를 볼 것인가 |

기록은 CSV 네 개에 쌓인다. `balances.csv`(월말 잔액), `expenses.csv`(지출),
`income.csv`(실제로 들어온 돈), `business_costs.csv`(업무 경비).

`cashflow_plan.yaml` 의 수입이 "들어올 예정"이라면 `income.csv` 는 "들어왔다"다.
둘을 섞지 않는 이유는 예정과 실제가 어긋나는 폭 자체가 정보이기 때문이다.

설정과 기록이 앞뒤가 맞는지는 `./fin validate` 가 봐준다.

## 이 체계가 붙잡고 있는 세 가지 원칙

**1. 순자산이 아니라 유동자산으로 센다.**
전세보증금 1.5억은 순자산에는 잡히지만 다음 달 생활비가 될 수 없다.
계좌마다 유동성 등급(`instant` / `short` / `long` / `locked`)을 매기고,
런웨이는 실제로 꺼낼 수 있는 돈만으로 계산한다. IRP·연금저축·보증금은
아무리 커도 런웨이에 들어가지 않는다.

**2. 평균을 오염시키지 않는다.**
결혼식 두 건이 겹친 달을 그대로 평균에 넣으면 "앞으로 매달 축의금을 낸다"는
계산이 된다. 지출은 `fixed`(고정비) / `variable`(변동비) / `irregular`(비정기)로
나누고, 소진 속도 평균에는 앞의 둘만 쓴다. 비정기 지출은
`cashflow_plan.yaml` 에 **시점을 지정해서** 따로 떨어뜨린다.

**3. 업무 경비는 생활비와 섞지 않는다.**
현장을 오가며 낸 통행료와 주유비를 개인 지출에 넣으면 소진 속도가 부풀고,
그 숫자를 보고 엉뚱한 긴축을 하게 된다. 원장을 아예 분리했다
(`business_costs.csv`). 다만 정산받기 전까지는 실제로 내 통장에서 나간
돈이므로, 이 원장은 '얼마 썼나'보다 **'얼마를 아직 못 받았나'**를 추적한다.

**4. 과거를 고쳐서 미래를 맞추지 않는다.**
끝난 구독이나 곧 생길 보험료를 반영하겠다고 지난달 기록을 손대면 그 달의
진실이 사라진다. 기록은 그대로 두고 `profile.yaml` 의 `burn_adjustments` 로
앞으로만 조정한다. 리포트는 기록 평균과 조정 후 값을 나란히 보여주므로,
조정이 얼마나 개입했는지 항상 보인다.

**5. 하나의 숫자를 믿지 않는다.**
런웨이는 항상 네 갈래로 본다 — 기본 / 긴축 / 최악 / 투자자산까지 헐 때.
실업급여는 `confidence: expected` 라서 최악 시나리오에서는 빠진다.
의사결정의 기준은 기본 시나리오가 아니라 **최악 시나리오의 소진 시점**이다.
그게 실질적인 마감기한이다.

## 명령어

| 명령 | 하는 일 |
|---|---|
| `fin` / `fin status` | 자산 · 소진속도 · 런웨이 · 임박한 기한을 한 화면에 |
| `fin runway` | 시나리오 비교 |
| `fin runway --scenario worst` | 그 시나리오의 월별 현금흐름 표 |
| `fin report --month YYYY-MM` | 그 달의 수입 · 지출 · 순현금흐름 |
| `fin checklist` | 퇴사 후 행정 절차와 기한 |
| `fin accounts` | 계좌별 잔액과 유동성 |
| `fin spend <분류> <금액>` | 지출 기록 (`3.2만`, `1.5억` 같은 표기도 됨) |
| `fin earn <출처> <금액>` | 수입 기록 |
| `fin cost <현장> <분류> <금액>` | 업무 경비 기록 |
| `fin costs` | 업무 경비 리포트 · 미정산 잔액 |
| `fin snapshot --set <계좌id>=<금액>` | 월말 잔액 기록 (안 적은 계좌는 지난달 값을 이어받음) |
| `fin validate` | 설정 오류와 앞뒤 안 맞는 기록 찾기 |

## 주의

- **실제 원장(`data/balances.csv`, `data/expenses.csv`, `data/income.csv`)은 기본적으로
  git 추적에서 빠져 있다.** 이 리포지토리가 public이면 지출 내역이 그대로
  공개되기 때문이다. private으로 바꿨다면 `.gitignore` 의 마지막 두 줄을
  지워라 — 그때부터 자산 변화가 git 이력으로 쌓인다.
- 행정 기한은 제도 변경에 따라 달라진다. `checklist.yaml` 의 날짜는 "언제
  알아봐야 하는지"를 알려주는 알람이지 법적 기한 그 자체가 아니다.
  신청 전에 반드시 공단·고용센터·홈택스에서 확인할 것.
- 이 도구는 세무·투자 자문이 아니다. 계산은 정직하지만 판단은 사용자 몫이다.
