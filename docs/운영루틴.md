# 월간 운영 루틴

자산관리 도구가 실패하는 이유는 계산이 틀려서가 아니라 안 쓰게 되기
때문이다. 그래서 루틴은 짧아야 한다. 아래는 매달 10분이면 끝난다.

## 매일 — 30초

쓴 돈을 그 자리에서 남긴다. 분류를 고민하지 말 것. 나중에 고치면 된다.

```bash
./fin spend 식비 12000 --memo "점심 배달"
./fin spend 구독 8990 --kind fixed --memo "배민클럽"
```

들어온 돈도 같은 방식으로 남긴다. 소득 공백기에는 수입이 드물어서 오히려
빠뜨리기 쉽고, 빠뜨리면 소진 속도가 실제보다 빠르게 계산된다.

```bash
./fin earn 구직급여 189만 --memo "1회차"
./fin earn 이자 62000
```

`--kind` 기본값은 `variable`이다. 매달 자동으로 빠져나가는 것만 `fixed`,
결혼식·자동차세·명절처럼 어쩌다 한 번인 것만 `irregular`로 찍으면 된다.
이 구분 하나가 소진 속도 계산의 정확도를 결정한다.

### 취소된 거래는 적지 않는다

카드 앱에서 **거래취소**로 표시된 건은 기록하지 않는다. 선승인 후 취소,
중복 결제 취소가 흔한데 그대로 적으면 지출이 두 배로 잡힌다.

확인하는 법은 간단하다. 카드 앱의 그날 합계와 내가 적은 합계를 맞춰보면
된다. 예를 들어 9월 1일 화면 합계가 49,650원이었고, 취소 2건을 뺀
5건의 합이 정확히 49,650원이면 제대로 뺀 것이다.

### 업무 경비는 다른 원장에

일하면서 쓴 돈은 `fin cost` 로 따로 남긴다. 개인 소진 속도에 들어가지 않는다.

```bash
./fin cost 고양·정릉 톨비 3400
./fin cost 고양·정릉 주유 50000 --memo "현장 이동"
./fin costs                      # 이번 달 경비와 미정산 잔액
```

`settled` 는 **내 통장에서 나갔는가**와 **돌려받을 것인가**를 함께 담는다.

| 값 | 내 통장에서 나갔나 | 돌려받나 |
|---|---|---|
| 미정산 (빈 값 포함) | 나감 | 받을 예정 |
| 정산완료 | 나갔다가 돌아옴 | 받았음 |
| 법인카드 | 안 나감 | 해당 없음 |
| 자부담 | 나감 | 안 받음 |

법인카드로 결제하면 개인 현금흐름에는 영향이 없지만 **예산 소진률에는
그대로 잡힌다.** 회사 돈이라고 안 세면 한도를 넘긴 걸 모르게 된다.

개인 돈으로 내고 정산을 기다리는 구조라면, 미정산 금액은 사실상 나에게
갚아야 할 돈이다. 소득이 없는 기간에 이게 쌓이면 통장 잔고는 줄어드는데
순자산은 안 줄어드는 상태가 된다. 정산 주기를 짧게 가져갈수록 좋다.

### 이 원장에 무엇이 들어오고 무엇이 안 들어오는지

계산은 들어온 기록만큼만 정확하다. 지금 기준으로 원장에 들어오는 것과
안 들어오는 것을 적어둔다.

| 결제 수단 | 성격 | 원장에 들어오나 |
|---|---|---|
| 현대카드 Summit | 개인 카드 | 들어옴 (개인 지출 + 개인 카드로 낸 경비) |
| 네이버 현대카드 | 개인 카드 | 들어옴 |
| 체크카드 | 개인 | 들어옴 |
| M BOOST 하이패스 | 톨비 전용 | 들어옴 |
| **법인카드** | 회사 | **안 들어옴** |

법인카드 내역이 빠지므로, 그 카드로 경비를 쓰고 있다면 **예산 소진률은
실제보다 낮게 나온다.** 대시보드의 "종료 시 총액"은 그 경우 하한선이다.
개인 소진 속도에는 영향이 없다 — 법인카드는 어차피 개인 자산을 줄이지 않는다.

### 한도 안에서 움직이는지는 하루 단가로 본다

소진률만 보면 늦다. "64% 썼다"가 문제인지 아닌지는 며칠이 지났고 앞으로
며칠 더 나가야 하는지에 달려 있기 때문이다. 그래서 `fin costs` 는 비율
대신 **하루 단가**를 기준선으로 쓴다.

```
허용 단가 = 한도 ÷ 예상 현장 일수
```

실제 하루 단가가 이 선 아래면 몇 번을 나가든 한도 안에 들어온다. 위로
올라가는 순간 일수를 줄이든 단가를 낮추든 해야 한다. 리포트의 `여유`
줄이 그 차이이고, 음수가 되면 그 페이스로는 한도를 넘긴다는 뜻이다.

`남은 예산 N일치`는 남은 금액을 하루 단가로 나눈 값이다. 달 중간에
"앞으로 몇 번 더 나갈 수 있나"를 묻는 가장 실용적인 형태다.

이번 달 현장 일수가 3일 미만이면 하루 단가와 예상 일수를 지난달에서
빌려온다. 한 번 나간 날을 그 달 전체로 늘려 잡으면 예측이 요동치기 때문이다.
월말 추정은 5일이 지나기 전에는 아예 내지 않는다.

### 예산은 매달인지 총액인지가 전부다

`business_budget.yaml` 의 `period` 하나로 읽는 법이 완전히 달라진다.
같은 100만원이라도 `monthly` 면 한 달 64만원은 한도 안이고, `total` 이면
프로젝트 예산의 64%를 한 달에 쓴 것이다.

총액 예산에 `end_date` 를 넣으면 질문이 하나 더 붙는다 — **종료일까지
버티는가.** 남은 기간에 몇 번 더 나갈지를 지난달 출근율로 추정해서
끝까지 계산한다.

```
남은 기간 예상 = 남은 일수 × 출근율 × 하루 단가
종료 시 총액   = 지금까지 쓴 돈 + 남은 기간 예상
```

경비는 매일 나가지 않으므로 달력 일수로 곱하면 과대 추정된다. 그래서
출근율(현장에 나간 날 ÷ 그 달 일수)을 끼워 넣는다.

여유가 예산의 5% 미만이면 경고를 띄운다. 계산상 맞아떨어져도 하루 단가가
조금만 올라가면 모자라기 때문이다.

### 할부는 다르게 적는다

할부는 **1회차만 그 달에 `irregular` 로** 적고, 나머지 회차는
`cashflow_plan.yaml` 의 `scheduled_expenses` 에 월을 지정해 넣는다.

```yaml
- id: installment_clothing
  name: 아울렛 할부 잔여 (3개월 중 2·3회차)
  amount: 484_200
  months: [2026-09, 2026-10]
```

이렇게 해야 소진 속도 평균은 부풀지 않으면서, 앞으로 확정된 지출은
런웨이에 빠짐없이 반영된다. 둘 다 `variable` 로 적으면 평균이 오염되고,
둘 다 빼면 없는 돈을 있다고 계산하게 된다.

소득이 없는 동안 할부는 소비가 아니라 부채다. 이번 달 결제가 다음 몇 달의
선택지를 미리 없앤다.

## 매월 말 — 10분

### 1. 잔액을 찍는다 (3분)

계좌 앱을 열어 잔액만 옮긴다. 지난달과 같은 계좌는 안 적어도 자동으로
이어받으므로, 바뀐 것만 적으면 된다.

```bash
./fin snapshot --set main_checking=5200000 --set parking=17500000
```

### 2. 앞뒤가 맞는지 본다 (1분)

```bash
./fin validate
```

두 방향으로 본다.

- "유동자산은 X원 줄었는데 기록은 Y원뿐" → **빠뜨린 지출**이 있다. 큰 것
  하나가 안 잡혔을 확률이 높다.
- "기록보다 유동자산이 X원 덜 줄었다" → **기록하지 않은 수입**이 있다.
  환급, 이자, 중고거래처럼 잊기 쉬운 것들이다.

### 3. 그 달을 읽는다 (3분)

```bash
./fin report
```

볼 것은 세 개뿐이다.
- **순현금흐름.** 이 달에 자산이 실제로 얼마나 줄었는가. 이 숫자가 곧
  런웨이의 기울기다.
- **고정비 비중.** 절반을 넘으면 변동비를 조여도 소용없다. 구독·통신·보험
  같은 고정비 자체를 끊어야 한다.
- **전월 대비.** 늘었다면 어느 카테고리가 늘었는지 한 줄로 보인다.

### 4. 런웨이를 확인한다 (3분)

```bash
./fin
```

이 한 화면에서 판단할 것:

| 보이는 것 | 그러면 |
|---|---|
| 최악 시나리오가 목표 개월 수 아래 | 지금이 구조를 바꿀 시점. 다음 달이 아니라 이번 달. |
| "월 지출을 N원 이하로 줄여야" 문구 | 그 숫자가 다음 달 예산이다. |
| 기한 알림에 `!` 표시 | 돈 계산보다 먼저 처리할 것. |

### 고정비가 바뀌면 조정을 넣는다

구독을 끊었거나, 비용이 다른 곳으로 넘어갔거나, 새 고정비가 생겼는데 아직
기록에 없다면 `profile.yaml` 에 적는다.

```yaml
burn_adjustments:
  - name: 클로드 맥스 (9월부터 법인 비용)
    amount: -161_227
  - name: 건강보험 지역가입 보험료
    amount: 120_000
```

지난달 기록을 고쳐서 맞추면 안 된다. 그 달에 실제로 그 돈이 나갔다는 사실이
사라지기 때문이다. 과거는 그대로 두고 앞으로만 조정한다.

새 달의 기록이 쌓여 평균에 자연히 반영되면 해당 항목을 지운다.

## 분기마다 — 30분

1. **`cashflow_plan.yaml` 갱신.** 실업급여 수급이 확정됐으면 `confidence`를
   `expected` → `confirmed` 로 올린다. 끝나가는 수입의 `end` 월을 확인한다.
2. **시나리오 재설정.** 긴축 시나리오의 절감률이 현실적인지 본다. 3개월간
   한 번도 그 수준으로 못 살았다면 그건 계획이 아니라 희망이다. 숫자를 올려라.
3. **`scheduled_expenses` 확인.** 다음 6개월 안에 오는 큰 지출(종합소득세,
   자동차보험, 명절)이 다 들어가 있는지 본다. 여기 빠진 게 런웨이를
   가장 크게 흔든다.
4. **자산배분 점검.** 투자계좌가 `long` 등급이라 런웨이 2차 재원으로만
   잡혀 있다. 1차 재원(현금성)이 최악 시나리오 기준 6개월 미만이면,
   투자자산 일부를 현금성으로 옮기는 것을 고려한다. 소득 공백기에는
   기대수익률보다 **팔아야 할 때 손실 구간이 아닐 것**이 더 중요하다.

## 재취업하거나 소득이 생기면

1. `cashflow_plan.yaml` 의 `incomes` 에 급여를 넣는다.
2. `profile.yaml` 의 `emergency_reserve` 를 올린다 — 이번 공백기에 얼마가
   필요했는지 이제 실제 숫자로 안다. 그 값을 쓰면 된다.
3. `checklist.yaml` 의 남은 항목을 정리한다. 특히 종합소득세 신고는
   재취업해도 사라지지 않는다.
